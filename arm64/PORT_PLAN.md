# Code: Veronica X — Android ARM64 port plan

**Current presentation scope:** the user's subsequent request added a virtual
room and direct Quest Touch input around the original 4:3 game screen. That
host is now in use; the flat-only/OpenXR exclusions in the initial milestones
below describe the earlier plan. The archived replacement VR gameplay remains
excluded. The original engine and campaign are still the porting target.

**Outcome:** a standalone Android `arm64-v8a` APK that opens as a flat-screen app on Quest 3. It runs the original game engine from a user-supplied PS2 NTSC-U disc image (SLUS-20184). From a clean install, New Game must play the original opening, hand control to the player, and support playing the campaign through the ending and credits with working saves. Preserve original gameplay, camera, menus, scripts and content. Route controller input through the original pad interface. OpenXR, VR controls, PC enhancements and other disc regions are outside the initial release.

**Starting point:** the upstream engine still builds for 32-bit hosts and its desktop build guard is intact. The Android NDK checks for EE memory/DMA, scalar VU, and original opening assets run natively on Quest 3. They do not start the game. The Ninja ABI probe shows why changing compiler flags is insufficient: native pointers expand the 24-byte model record to 32 bytes and the 52-byte object record to 72 bytes.

**Architecture:** keep PS2-format records and emulated device addresses fixed-width. Decode disk data into native engine work structures; use checked guest addresses where the original engine emits DMA, VIF or GS packets. Keep the original game loop and gameplay code. Use the archived Quest work as reference for portable subsystems only; keep its alternate gameplay implementation and VR host out of the app.

## How to catch regressions

- Compare the 32-bit reference and ARM64 engine at named checkpoints: room and character IDs, flags, player position, inventory, motion/frame indices and save checksums. Compare image/audio captures with documented tolerances where hardware or timing differs. Investigate game-state divergence before tuning presentation.
- Keep a small fast suite for ABI, DMA/VIF, VU, disc reads, asset decoding and save round trips. Run it with the NDK toolchain on every engine change, and run the ARM64 binaries on Quest for each milestone. Add a reproducer for each crash or progression fix. Use bounds checking and sanitizers in developer targets where supported.
- Never count a boot, room viewer or late-game save as proof of a complete playthrough. Track the first failing original scene or input, the subsystem involved and the reference result.

## Active execution order (2026-11-21)

The user requested the following sequence. These are acceptance stages, not
claims that the installed game can already complete them.

1. **In progress - normal enemies:** retain native enemy motion provenance,
   integrate original initialization and ordinary pose blending, then port the
   hostile controller dispatch, perception, movement, attack, damage and death
   paths with their original collision, animation and sound dependencies.
2. **Pending - player integration:** original head control, damage reactions,
   enemy contact and room interactions. Finish the remaining original player
   movement/controller paths needed by the opening and first transition.
3. **Pending - complete opening presentation:** connect original camera,
   effects and cutscene sequencing in the real per-frame runtime; validate
   continuous execution rather than isolated handlers alone.
4. **Pending - opening acceptance:** run New Game through the entire opening,
   verify player-control handoff, the first authored room transition and a
   save/load round trip against original state and presentation checkpoints.
5. **Pending - runtime enablement and campaign:** enable full readiness only
   after stage 4 passes, then expand scenario coverage through the campaign.

The installed full-runtime gate remains in place. Isolated fixtures and the
old visible locomotion preview do not establish completion of these stages.
